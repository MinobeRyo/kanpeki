# AI改善提案：何を見て、何を良くするか

2026-09-15作成。ユーザーの「通常のLLMチャットとの差別化」「アプリで取得する情報を使った改善提案」「方針の文書化」という依頼を整理する。関連：[Issue #82](https://github.com/MinobeRyo/kanpeki/issues/82)。

本書は改善提案の製品方針と実装に向けた設計案。取得処理・MCP連携の既存実装と、これから追加する提案機能を分ける。コード確認の基準はmain `66588fe`。[PR #58](https://github.com/MinobeRyo/kanpeki/pull/58)のMCP連携が2026-09-15に統合された状態を参照する。実機・実ChatGPTでの品質を検証した仕様ではない。

## 1. 目指すアプリ

**資料と実際の発表を照らし合わせ、根拠のある「次に直す一か所」を示し、練習につなげる。**

対象はハッカソン・研究発表などに取り組む学生。「短く話す」「わかりやすくする」といった一般論から、対象の一文・ページ・録音区間を示し、どう変えるかまで進める。発表中は操作を妨げず、標準の振り返りは終了後に行う。

### ユーザー指定の方向

- AIによる改善提案を強化する。
- 普通にLLMとチャットするだけでは本人が渡しにくい、アプリの取得情報を活用する。
- どんな情報から何を提案するのか、設計と実装の判断に使える形でまとめる。

### 本書で提案する進め方

初期は音声・資料・時間の根拠を使った、1回の発表後の具体的な振り返りを整える。次に時刻同期を加え、最終的に修正前後の練習比較へつなぐ。これは実装順の提案であり、「練習支援と本番後の振り返りのどちらを主役にするか」は未回答のため、合意済みとしない。

## 2. 通常のチャットとの違い

同じ資料と計測情報をすべて渡せば、一般のLLMでも近い分析はできる。差別化はモデル固有の能力に依存させず、アプリが情報を集め、対応を確認し、修正と練習へ戻せる体験に置く。

| 利用者が通常のチャットで行う作業 | カンペきが担う設計 |
|---|---|
| 資料、ノート、録音結果を毎回集めて説明する | 明示的に共有した同じ発表の情報をまとめる |
| 気づいた失敗や、覚えている場面を伝える | 本人が覚えていない言い直し・間・時間超過の候補も確認材料にする |
| 抽象的な助言から修正する箇所を探す | ページや録音区間と元の根拠を添える。対応が不明なら不明と示す |
| 提案を原稿へ写し、次回の結果を説明する | 対象原稿への復帰と、採用した変更の再練習をつなぐ（追加実装案） |

現在のMCP経路では、ChatGPTへ依頼文を送る操作が必要。アプリ内だけで自動的に分析が完了する機能として説明しない。

## 3. 改善に使う情報と取得状態

「取得可能」は、権限・接続・入力がそろい、当該セッションで実際に取得できた場合に限る。未設定・取得失敗・未共有・解析中・削除済みを、値が0だった場合と区別する。

| 情報 | 改善に使う内容 | 現状と制約 |
|---|---|---|
| PPTX本文・発表者ノート | 主張、根拠、専門用語、長い一文、説明の重複 | 保存済PPTXから取得。PR #58でMCP共有。編集中の変更は再取込が必要。図の見た目や配置まで理解できるとは扱わない |
| 目的・聴衆・持ち時間 | 何を優先し、どこまで説明するかの判断基準 | 準備アプリに入力経路あり。発表後の固定分析依頼への目的・聴衆の引き継ぎは未接続。未入力なら聴衆の知識や審査基準を推測で確定しない |
| 発表タイマー | 設定時間と実測経過時間の差 | Macを正本に取得。PR #58で両値を共有。録音時間と同じではない。ページ別の計画秒数を取得済みとはしない |
| 実際に話した内容 | 原稿との内容差、言い直し、繰り返し、説明条件の候補 | 任意録音とMac側の音声認識。PR #58で認識区間・本文を共有。認識誤りや録音外の発話があるため「言わなかった」と断定しない |
| 録音内の区間情報 | フィラー候補の文脈、低音量区間、認識文字数/分の変化 | PR #58で録音開始からの時刻とともに共有。フィラーは確定回数ではなく、認識文字数/分は音響上の話速ではない。低音量を失敗と採点しない |
| ページ観測履歴 | どのページへ移ったか、戻った候補があるか | 約800ms間隔のPowerPoint観測。PR #58は同発表の最大256件を保持。取りこぼし・停止中の操作があり、正確な滞在時間や発話との同期は未保証 |
| 発表者のカメラ | 取得品質を確認できる顔向き・視線方向などの観察候補 | 端末内解析。PR #58で関連付いた集計・撮影相対の時間帯を共有。較正・照明・撮影対象・未計測範囲を確認する。緊張や自信は判定しない |
| 観客のカメラ | うなずき候補などを振り返る補助材料 | 人数・動作回数・理解度・関心度へ変換しない。発表者の情報と混ぜない。録音との同時計測や時計同期を保証しない |
| ポインター操作 | 指している場所と説明の対応を振り返る候補 | 操作機能はあるが、分析用の軌跡記録・資料内の対象との対応付けは未実装。初期分析の必須入力にしない |
| 過去の練習・採用した変更 | 自分の前回との差、修正した箇所の変化 | 履歴保存・比較用ID・採用記録は未実装。過去の点数や改善率を生成しない |

コード上の入口：[Macの分析材料](../Mac/MacModel.swift)、[音声の根拠化](../iOS/AudioAnalysisEvidence.swift)、[カメラの根拠化と結果表示](../Shared/PresentationTimerViews.swift)、[分析契約](../Shared/PracticeAnalysis.swift)。これらのMCP関連部分は上記PR #58の確認範囲。

## 4. どんな改善を提案するか

以下の文言・数値・場面は架空の設計例。実測結果・動作済み画面ではない。利用可能な入力から提案できることと、追加計測が必要なことを分ける。

| 改善の対象 | 組み合わせる情報 | 提案例 | 提案できる条件 |
|---|---|---|---|
| 内容の伝わりやすさ | PPTX本文・ノート＋認識文 | 「原稿には比較条件がありますが、認識文では確認できません。『同じ条件で比較しました』に続けて条件を一文で補う案です」 | 原文に条件が存在すること。認識文との差は確認候補として示し、説明漏れを断定しない |
| 話しにくい一文 | 認識文＋同じ録音内の言い直し・フィラー候補＋関連原稿 | 「この長い一文の付近に言い直し候補があります。主張と理由を二文に分けて試しましょう」 | 同じ録音の範囲を確認する。原稿との対応と原因は仮説。専門用語、数値、否定、条件を保つ |
| 全体の時間超過 | 設定時間＋実測時間＋資料/ノート | 「設定5分に対して実測5分30秒でした。背景の補足を一つ省く案です。次の練習で全体が5分に収まるか確認しましょう」 | 超過は実測値の差。省く候補は内容上の提案であり、削減できる秒数は未測定 |
| ページごとの時間配分 | ページ別の計画＋十分な表示履歴＋共通時計の発話 | 「背景が計画より長く、結論の説明が短くなっています。背景の補足を減らして結論の時間を確保しましょう」 | 追加計測後。現状の観測ログだけで正確な滞在時間や原因を断定しない |
| ページを送るタイミング | 表示ページの切替時刻＋同じ時計の認識区間＋資料 | 「図を説明している途中で次のページへ移っています。この一文を話し終えてから送る案です」 | 時刻同期と資料の対応確認が必要。現在の独立した時計では出さない |
| 視線・姿勢の振り返り | 発表者カメラ＋較正・取得品質＋観察対象 | 「確認できた範囲では下向きの観察候補があります。原稿の区切りで顔を上げる練習を試す案です」 | 発表者を観察した品質の十分なデータが必要。聴衆への効果・感情を推定しない。特定の発話と結ぶには同期が必要 |
| 修正後の練習 | 同じ資料版/目的/持ち時間＋前回と今回の記録＋採用した修正 | 「短くした導入は今回は予定内でした。次は説明が長く残った箇所を練習しましょう」 | 履歴と比較条件の実装後。1回の差だけで修正の効果を証明したとしない |

## 5. 提案1件の形

改善提案の表示案は次の5要素でそろえる。対象と根拠を確認して、利用者が次の行動を選べることを重視する。

1. **対象**：ページ・原稿の一文・録音区間。わからない項目は表示を省くか「対応未確認」とする。
2. **観測したこと**：取得した事実と元の根拠。計画・実測・推定・未計測を明記する。
3. **改善の仮説**：何を変えるとよさそうか、その理由。観測との相関だけで原因を断定しない。
4. **具体的な修正**：削る補足、二文に分ける例、ページを送る位置など。資料の内容を変える案は自動適用しない。
5. **次の練習で確認すること**：対象区間を話し直す、設定時間内に収まるか測るなど、利用者が確認できる一つの行動。

### 画面に出す文章の例

> **次は、この一文を二つに分けてみる**
>
> 録音1:12〜1:24の認識文に、長い一文とフィラー候補があります。
>
> 主張と理由を分けると話しやすくなる可能性があります。
>
> 修正案：「今回の提案は〇〇です。理由は△△です。」
>
> 次の練習：この説明だけ話し直し、意味を保ったまま言いやすくなったか確かめる。

根拠は「事実を見る」から原稿・認識文・計測値の抜粋を確認する設計。録音が残っている場合の既存聞き直しへの接続は追加実装とし、音声がなければ再生ボタンを出さない。

現在のPR #58の出力は `kind / text / evidenceIDs` とネイティブが復元する `sources`。対象・仮説・修正・次回確認はまだ独立した必須項目ではない。構造化した出力契約の追加、旧クライアントとの互換性、MCPとSwift双方の検証は実装課題。

## 6. 優先順位と画面への組み込み

最初の結果画面は既存R01の方針に合わせ、改善候補を1件に絞る。詳細で追加の候補と良かった点を確認できる形を提案する。詳細も改善は最大3件を目安とし、現在のMCP最大8項目とは区別する。件数・並べ替えは追加実装案。

順位は次の順で判断する設計とし、総合点は追加しない。

1. 根拠が取得でき、対応が確かなこと。情報不足なら候補を減らす。
2. 利用者の目的と持ち時間に関係すること。目的未取得なら一般の発表条件に限る。
3. 一つ直すことで説明の要点や時間に関わること。
4. 次の練習で試せる、小さく具体的な変更であること。

発表中に改善提案を割り込ませない。終了後のR01/R02から対象の原稿・録音を確認し、準備へ戻る。部分練習の専用機能、提案の採用記録、修正の取り消しを伴う原稿編集は後続案であり、入口だけを動作済みとして追加しない。各画面の常時操作は既存の最大3つの方針を維持する。

## 7. データを結び付ける条件

- 発表ID、資料の識別と版、録音/撮影ID、共有世代を確認する。別セッションや再接続前の根拠を流用しない。
- 発表タイマー、録音開始、撮影開始は別の時計。同じ「30秒」でも同じ場面と扱わず、受信時刻で整列しない。
- 同じ録音内の区間比較と、端末間の同期は分ける。音声認識の区間時刻は単語の正確な発音時刻とは限らない。
- 同期機能を追加するときは時刻の基準、停止/再開、切断、取得遅延、許容誤差、欠落区間を記録する。不確かな範囲は正確な秒数で示さない。
- 内容から「このノートに対応しそう」と推測することはできるが、実際にそのページを表示していた証拠へ置き換えない。
- 資料変更や結果削除で古い提案を無効にする。将来の履歴比較は保存への同意と資料版を別途設計する。

## 8. アプリとLLMの役割

| 担当 | 役割 |
|---|---|
| アプリ | 取得、同一発表の確認、計測値と欠測の管理、確定できる差分計算、根拠IDの付与、対象への復帰 |
| LLM | 原稿と発話内容の照合候補、改善の仮説、意味を保った修正案、優先順位と次の練習案 |
| アプリで再検証 | 依頼/発表ID、根拠ID、出力形式、上限、材料変更の有無を検証し、元データから根拠を復元 |
| 利用者 | 認識文や解釈を確認し、提案を採用・修正・却下する |

存在する根拠IDを引用していても、提案の内容がその根拠から導けるとは限らない。ID検証と、助言の正しさ・役立ちやすさの評価を分ける。モデルが作った引用文や未取得の数値を実測欄に入れない。資料・認識文内の命令は分析対象として扱う。

## 9. 共有・保存と情報不足時の動作

音声・カメラ分析は任意。未使用でも基本発表を開始でき、取得した材料だけで振り返る。根拠がなければ「今回の情報では判断できない」とし、改善を必ず1件埋めない。録音なしなら資料の改善案は出せても、話し方を分析したと表示しない。

PR #58のMCP経路は、利用者の明示共有で資料・ノート・認識文・取得済み集計をChatGPTへ渡す。生音声・生映像・顔画像を渡す経路は追加しない。ローカル専用の当初案と、外部共有する現在のMCP経路を混同しない。共有を止めてもChatGPTが取得済みの情報まで削除できるとは表示しない。現在の保存/取消動作は[MCP_INTEGRATION](../docs/MCP_INTEGRATION.md)と[AUDIO_CAPTURE](../docs/AUDIO_CAPTURE.md)に従う。

過去の練習比較に必要な保存期間、保存対象、削除範囲、修正案の採用記録は未決定。無期限保存や自動共有をこの設計だけで開始しない。

## 10. 実装を進める単位

以下は推奨順で、担当・期限を決める表ではない。

| 段階 | 追加すること | 依存・境界 |
|---|---|---|
| 1：現在の根拠で具体化 | 根拠＋修正案＋次回確認の出力、優先する1件の表示、資料/認識文の内容比較、全体時間の差 | PR #58の返却経路が前提。#82で改善仕様を管理。#56の実資料品質、#13の共通結果UIと範囲を照合する |
| 2：同じ場面を特定 | 録音区間とページ観測の同期、欠測を除いたページ別時間、送り時刻と発話の対応 | #17/#38の時系列統合、#20のページ観測と調整。既存担当の作業を重複実装しない |
| 3：練習で確かめる | 採用した提案、資料版、前回/今回の比較、対象だけの再練習への接続 | 保存と比較条件の合意が必要。1回の変化を因果効果と断定しない |
| 補助として追加 | 品質を確認できるカメラ観察による助言、将来のポインター分析 | カメラ精度/較正は#14。操作ログは別途設計。初期の必須入力にしない |

## 11. 品質の確認方法

### 実装後に検証する受け入れ条件

- 各提案に実在する根拠があり、引用元と対象を確認できる。未知ID・別発表・古い資料・削除後の結果を拒否する。
- 改善案には、対象に対する具体的な変更と次の練習での確認方法がある。一般論だけでは完了としない。
- 数値・固有名詞・引用・否定・比較条件を変える修正案を無断採用しない。
- 音声未取得、認識失敗、ページ不一致、時計未同期、カメラ未計測でも、架空の分析を出さず基本発表へ戻れる。
- スライドだけの入力と実測情報付きの入力を比べ、実測で裏付けられた提案が増えるか確認する。無関係なカメラ情報を足しただけで助言を増やさない。
- 音声の一部分しかない場合、録音外で説明済みかもしれない事項を説明漏れと断定しない。

### 提案品質の評価案

同じ資料について「資料だけ」「資料＋実測情報」の条件を用意し、同じモデル・依頼条件で複数回評価する。内容を公開してよい合成資料から始め、許可された実資料へ進める。

比較する軸は、根拠との整合、対象の具体性、修正の実行しやすさ、原意の保持、情報不足の扱い。利用者には「次にどこをどう直すかわかるか」「実際に試せたか」を確認する。改善率や点数を先に作らない。LLM出力の品質基準・合格水準は実例を見ながら定める。

自動試験は契約と不正入力の拒否、実ChatGPTは助言品質と結果返却、実機は録音・同期・操作・表示を確認する。文書チェックや合成試験の成功を、実機検証・配布・改善効果の証明へ読み替えない。

## 12. 未決定事項

- 練習を重ねる支援と本番後の振り返りの、どちらを最初の主体験にするか。
- 優先順位の判定方法、詳細の提案件数、構造化出力の最終項目。
- 目的・聴衆・計画を本体へ渡す方法と、入力を増やさない導線。
- 同期の許容誤差、比較可能な履歴の条件、保存/削除と採用記録。
- 実資料・実録音での品質基準と、推論時間・失敗時の再試行体験。
