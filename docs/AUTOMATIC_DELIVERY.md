# マージからチームの確認まで

mainのアプリ・署名・CI関連変更はTestFlight CDが一度だけ検証し、iPhoneとMacを同じコミットから署名・アップロード・内部グループへの割当する。仕様書だけの変更はビルドしない。手動配布もTestFlight CDから行う。旧Mac TestFlight CDは案内のみで、二重配布しない。

必要なRepository VariablesはNATIVE_CI_ENABLED、IOS_TESTFLIGHT_ENABLED、MAC_TESTFLIGHT_ENABLED、SLACK_NOTIFY_ENABLEDをtrueにする。署名Secretsが不足すれば安価なLinux上の事前確認で停止する。署名はmainの配布ジョブだけが使用し、PRのコードへ渡さない。

新リポジトリのビルド番号は「1000 + TestFlight CD実行番号.再実行回数.0」。旧リポジトリの番号との重複を避けるための予約範囲であり、同じAppleアプリを別リポジトリから同時配布しない。再移植するときはAppleの最大番号を確認して新しい範囲を予約する。9000回目以降は番号方式の更新が必要。

Slackはマージ通知と配布通知を分ける。配布通知には両プラットフォームの版・Appleの状態・TestFlightリンクを表示し、変更点をスレッドに添える。内部テストはベータ審査を要求しないが、Appleでのビルド処理とテスターの招待受諾が必要。完了後および毎時にAppleを読み取り、処理中から内部テスト可能に変わると元の通知を更新する。毎時確認はLinuxのみでビルドを起動しない。最後の配布から30日でApple確認を止める。

通知状態はGitHub Actions Cacheに保存する（秘密情報なし）。キャッシュが削除・失効した場合は通知が再作成されることがある。不確かなSlack送信結果は自動再送せず、ログと既存通知を確認する。リンクは同じままなので、テスターはTestFlightで通知記載のビルド番号を選び更新する必要がある。OSの確認・TestFlightインストール・招待受諾は省略できない。

設定済みと配布成功は別。Issue #28の実行結果とApp Store Connectの対象内部テスト状態を確認するまで、最新アイコンが配布されたとは扱わない。
