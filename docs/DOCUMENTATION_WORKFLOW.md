# 実装と同時にドキュメントを更新する

2026-09-15のユーザー指示による運用。文書の自動生成・内容の自動保証ではなく、担当者の更新責任、PR宣言、機械検査、レビューを組み合わせる。

## 何をどこに書くか

| 変化 | 同じPRで確認・更新する文書 |
|---|---|
| 利用者の操作、機能、失敗時の復帰 | 関連するspecsと機能別docs。実装範囲が変わればSTATUS、入口が変わればREADME |
| データ契約、制約、対応OS、保存/削除 | 関連する仕様・開発手順・検証条件 |
| 起動、権限、設定、配布 | APP_SETUP、関連する配布/設定文書。未実施と確認済みを区別 |
| 検証結果や提出時に示す成果 | 機能別の検証記録。代表例はCODEX_EVIDENCE/HANDOFFへ根拠リンク |
| テストだけ、内部整理、意味を変えない修正 | 文書への影響を検討し、更新不要ならPRへ具体的な理由 |

docs/STATUS.mdを現状の入口とし、仕様の合意、実装、main統合、CI、実機確認、TestFlight配布を別々に記す。確認日と根拠PR/Issueを付ける。進捗の正本は引き続きIssue。PR中の実装をmainで利用可能と書かない。すべての変更でSTATUS全体を書き直す必要はない。

企画画像・プロンプト・過去の比較や実測記録は履歴として保存する。古い未実装表記には、現状への注記と参照を付ける。未決定案を完了条件へ勝手に昇格しない。秘密情報・資料原文・生録音などを根拠として公開しない。

## 担当者の完了条件

1. 着手時に関連文書を列挙し、Issueの対象範囲に含める。
2. 実装と同じbranch/PRで、操作・制約・未対応・検証範囲を更新する。文書だけ後回しのまま完了報告しない。
3. PR本文に以下の2行を記す。更新対象のパスと内容、または利用者向け仕様が変わらない理由を具体的に説明する。

```text
Docs-Impact: updated
Docs-Reason: docs/AUDIO_CAPTURE.mdの録音停止条件と実機未検証の範囲を更新しました。
```

更新不要なら`Docs-Impact: none`と具体的な理由を書く。`不要`、`TBD`、テンプレートの未記入は不可。履歴・生成プロンプトだけの変更は現行文書更新の代わりにしない。

4. レビューではコードと文書を照合し、リンク先、main/PRの区別、未計測の扱い、古い一括「未実装」の残存を確認する。
5. 最新main取り込み時に文書も再照合し、別PRの実装を巻き戻さない。根拠の取得ができなければ未確認と記す。

## 自動検査と限界

`Documentation impact` workflowはPR作成・push・本文編集時に宣言を確認する。`updated`なのに現行文書の追加/変更がない、`none`なのに文書を変更した、理由が未記入なら失敗する。PR本文はJSONファイルから読み、シェルへ展開しない。

`merge_preflight.py`も現在のPR本文と全変更ファイルで同じ検査をする。CI未実行・古いCIだけのPRでも、手順に従うマージは宣言を再確認する。branch保護設定は変更しないため、GitHubの直接マージ自体を強制的に禁止する仕組みではない。

検査は記述の正確さや関連性を判断できない。無関係な文書を一行触るだけ、具体性のない理由、矛盾した実装済み表示はレビューで差し戻す。チェック成功を「全ドキュメントが正しい」と表示しない。

ローカル確認:

```sh
python3 -m unittest discover -s Tests -p 'test_documentation_check.py'
python3 scripts/documentation_check.py --base origin/main --body-file /tmp/pr-body.md
python3 scripts/merge_preflight.py PR番号
```

## 既存PRへの移行

このルールを含むmainを取り込み、PR本文へ宣言を追加する。既存の関連文書差分はそのまま利用できる。コード変更がない場合は不要理由を明記する。CIの再実行後、最新preflightを通す。古いPRだからといって必須チェックを外す、成功結果を偽造する、保護を迂回することはしない。
