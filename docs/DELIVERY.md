# CI/CDの構成と確認範囲

2026-09-15更新：共通CIとMac/iPhone内部TestFlight配布は接続済みで、成功記録がある。[現在の運用](AUTOMATIC_DELIVERY.md)、[検証・配布根拠](STATUS.md)を参照。以下の安全条件は維持し、最新ビルド・全員の招待受諾は個別に確認する。

PR → 変更範囲の判定 → 関連テスト → 現行ルールを確認してマージ → 同一mainコミットの検証を一度実行 → iPhone／Macのビルド・署名・配布 → 状態確認 → Slackへ短い通知。

文書だけの変更はネイティブビルドを起動しない。未知の変更は検証対象にする。配布は成功した同一コミットだけを使い、古いmain、外部PR、失敗・キャンセルからの配布を拒否する。別配布処理ごとに同じCIを繰り返さない。

開始後に確認するもの: Xcode対象とバージョン、実際に意味のあるテスト、Appleチームとアプリ識別子、ビルド番号、配布先、Slack対象、GitHub Actions予算とSecrets設定権限。

証明書・APIキーは必要範囲を確認して現行workflowの参照先へ登録する（現在はrepository Secrets。[CD](CD.md)参照）。旧アプリのIDや秘密鍵を自動転記しない。署名中のジョブを新pushで中断しない。アップロード済み・審査待ち・配布可能は区別する。

準備ワークフローはアプリをテストしない。アプリ実装がない状態でcore/mac/phoneの必須チェックを成功させるダミー処理を作らない。

## 確定した配布先

MacとiPhoneの両方をネイティブアプリとして提供する。主なチーム確認経路はそれぞれのTestFlight。Macの公証DMGは補助経路として残す。Mac App Store向けSandboxとPowerPoint操作・画面取得の両立は実機で検証し、署名なしビルド成功だけで審査対応済みと扱わない。
Slackの `MAC_TESTER_URL` はMac用TestFlight招待URLを優先できる。未登録の間は存在しないリンクを表示しない。iPhone用とMac用を混同しない。
